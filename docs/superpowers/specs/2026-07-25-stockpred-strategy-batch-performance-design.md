# StockPred 策略批量回测提速设计

## 目标

在不改变同一数据快照下回测结果的前提下，将 StockPred 策略批量回测改为“轻量海选、按需物化完整报告”的可恢复执行系统，消除全量策略重复读数与逐股 CSV 落盘造成的主要瓶颈。

## 依据与范围

本设计针对批次 `batch_20260723T235856_26050a43` 暴露的问题：356 个策略中仅 124 个成功、5 个失败、227 个仍排队；成功策略的中位耗时约 10 分钟，已产生约 15 GiB、25 万个文件。当前实现会串行运行策略、在“策略 × 评估日”层级重复读取数据，并为每个策略输出数千个 OHLCV CSV 文件。

本设计包含：批次调度、海选与完整报告的产物契约、共享数据、恢复机制、进度指标与验收测试。

本设计不包含：变更因子定义、回测撮合规则、收益指标公式、跨快照复用数据，或为旧批次自动迁移完整产物。

## 不可变约束

- 比较结果必须继续绑定完整 `data_snapshot`、`comparison_key`、策略源码快照与回测参数。
- 评估日 D 的任何输入只能包含 D 时点可见的数据；缓存键必须包含快照版本与评估日。
- 同一固定快照和请求下，新旧引擎的入选股票、交易、净值和核心指标必须一致，除浮点舍入误差外不得改变结果。
- 已成功的策略或已物化的完整报告不可因恢复操作而重复执行或覆盖。
- Windows 环境下不得将大型 Pandas 面板在进程间序列化传递。

## 总体流程

```text
创建批次
  → screening（轻量海选）
  → screening_completed（候选清单与空间预估）
  → 用户显式请求 detail-reports
  → materializing（仅候选策略完整报告物化）
  → completed / completed_with_failures

任一活动阶段在心跳过期后 → stalled → resumable
```

### 第一阶段：轻量海选

所有策略均参与回测，以产生可横向比较的指标。每个成功策略保存：配置、策略源码快照、数据快照、比较键、指标、净值、持仓、交易、入选信号、全量 `signals.parquet` 与逐股票指标。海选阶段不输出逐股票 OHLCV 文件。

海选完成后默认按 `sharpe` 降序取前 20 个有限指标且有效评估比例达标的成功策略。调用方可以以明确的策略 ID 列表替换或追加候选；失败策略和没有有限排序指标的策略不可自动入围。

### 第二阶段：完整报告物化

完整报告由显式接口触发，不在海选结束后自动生成。物化任务仅接受第一阶段成功策略，先校验该策略的快照、比较键和摘要产物完整性，再按 `detail_manifest.json` 中的股票集合和日期范围读取行情并原子写入 OHLCV 详情。

物化不得重新计算因子、信号、选股、交易或净值；因此不会改变排名，也不构成第二次全量回测。`detail_manifest.json` 至少包含：`run_id`、`comparison_key`、完整序列化的数据快照、股票代码集合、`market_start`、`market_end` 和生成版本。

## 数据共享与执行模型

### 评估日共享

Alpha 策略海选从“逐策略跑完全部评估日”改为“按评估日处理所有策略”。对于一个评估日：

1. 从批次不可变数据上下文取得交易日历、PIT 股票池、价格和复权数据。
2. 构造批次所需的最大回看窗口面板。
3. 向每个策略提供与旧行为相同长度的窗口切片，计算该日分数并更新该策略自己的持仓状态。
4. 释放该评估日动态面板。

交易日历和静态维表在一个批次中只加载一次。动态面板以 `(snapshot_digest, eval_date, max_lookback)` 为键，仅在当前评估日内复用；不在内存中积累所有评估日，以限制峰值内存。

### 并发边界

初始版本先通过共享评估日面板消除重复 I/O，并在海选协调器内单进程执行因子计算。完成阶段计时后，只有不共享大型面板的任务才能进入受限的进程池：图策略执行和完整报告物化。

进程池默认最多 2 个 worker，受每批次内存上限、写入队列长度和系统负载约束。父协调器是唯一的 `reports.json` 和 `state.json` 写入者；worker 仅返回结果事件，防止并发 JSON 覆盖。扩大到 3–4 个 worker 必须由基准数据证明不会使 Lance 读取、SSD 写入或内存变成新的瓶颈。

## 持久化状态与恢复

批次状态新增 `phase`、`current_strategy_id`、`screening_done`、`screening_total`、`detail_done`、`detail_total`、`heartbeat_at` 与按阶段累计时长。策略状态新增 `attempt`、`phase_started_at`、`heartbeat_at` 和错误分类。

服务启动时扫描活动批次；若心跳超出阈值则原子标记为 `stalled`。恢复只会重排 `queued`、被中断的 `running` 或 `stalled` 项；成功项和已物化项保持不变。

确定性数据错误（如输入 NaN 比例超过阈值、快照缺表、参数校验失败）不重试。暂时性 I/O 错误最多重试一次，并记录每次尝试的错误类别与耗时。恢复或重试完成后，批次仅在全部策略和所请求报告均达到终态时进入 `completed` 或 `completed_with_failures`。

## API 与产物契约

- `POST /stockpred/strategy-batches`：创建轻量海选批次。
- `GET /stockpred/strategy-batches/{batch_id}`：返回阶段、进度、当前策略、候选清单、阶段计时和空间预估。
- `POST /stockpred/strategy-batches/{batch_id}/detail-reports`：提交 `{ "top_n": 20, "sort_by": "sharpe" }` 或 `{ "strategy_ids": [...] }`，创建物化任务。
- `GET /stockpred/strategy-batches/{batch_id}/events`：推送状态变化、心跳、策略完成和物化进度。

海选产物与详情产物必须分开保存。海选摘要可以被读取和比较，但完整 OHLCV 只写入详情目录或由详情状态明确引用；详情写入采用 staging 目录后原子替换。一次失败的详情物化不得损坏海选摘要或其他候选策略的详情。

## 可观测性

每个策略及批次均记录：

- `data_load`、`panel_build`、`factor_compute`、`execution`、`artifact_write` 的耗时；
- Lance 读取次数、行数、缓存命中和未命中次数；
- 产物文件数、字节数、重试次数；
- 当前阶段、评估日和心跳。

SSE 每次状态变化与固定频率心跳均发送上述进度的摘要。监控用阶段计时而不是单一总耗时判断是否卡住，从而区分数据读取、因子计算、撮合和落盘问题。

## 验收条件

### 正确性

1. 固定快照下，代表策略的新旧结果在排序规范化后具有相同的入选股票、交易、净值和核心指标；浮点字段使用明确容差比较。
2. 对同一个成功策略，第二阶段生成的 OHLCV 内容与旧式完整产物等价。
3. 重启期间中断批次可恢复；已成功策略不会重复运行，已物化报告不会重复写入。
4. 缓存不得向评估日输入未来数据；测试必须验证缓存键包含完整快照摘要和评估日。

### 性能与容量

1. 轻量海选每策略不超过 20 个文件、15 MiB。
2. 以 10 个覆盖不同 Alpha 复杂度的策略建立固定快照基准；在结果一致前提下，海选总墙钟时间应至少比当前基线降低 50%。
3. 基准报告必须包含各阶段耗时、读取次数、缓存命中率、输出文件数和字节数，作为是否扩大 worker 数的依据。

## 实施边界

实现应保持现有策略目录、数据快照和运行状态模块的职责清晰：批次协调器负责调度和唯一状态写入；批次数据上下文负责只读缓存；策略会话只维护单策略跨评估日的状态；详情物化器只从已保存结果生成详细产物。不得以在 API 请求中临时创建全新协调器的方式承担持续执行状态。
